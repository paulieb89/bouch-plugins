# BOUCH development plugins

`bouch-supervision` helps a supervisor recover project context, choose whether to work directly or delegate, inspect outcomes and carry work across sessions. Its existing name is retained so installations can upgrade. `bouch-engineering` supplies a narrowly triggered evidence-assessment skill usable independently by coding agents. Neither depends on Runner, Notion, the Registry, Eve, an MCP server or the other plugin.

Both packages have a portable root `plugin.json` and a thin Claude manifest under `.claude-plugin/`. Supervision also retains its existing `.codex-plugin/plugin.json` compatibility overlay. Skills live once under each package's `skills/`. The existing `.agents/plugins/marketplace.json` and `.claude-plugin/marketplace.json` list both packages using paths relative to the repository root. Both catalogues are named `bouch-plugins`. They have separate entries but now list the same nine plugins: seven local (the two development plugins, `bouch-character-performance`, `foundations`, `property`, `legal-os` and `bouch-game-assets`) and two externally sourced Git root entries, `bouch-agent-core` (commit `df1d28e27c4d466558c9c46b40b5d2ca168c96d2`) and `bouch-audio` (commit `3d94024fad5d5f2a239864e42c3dc2727364d588`). The Claude entries pin release tags `v0.2.6` and `v0.2.0` as well as these commits; the OpenAI entries pin the matching commit hashes only. In a fresh isolated Codex environment, this nine-entry local marketplace was discovered and both external plugins installed successfully, as versions 0.2.5 (Core) and 0.2.0 (Audio). In a separate isolated skill probe, Codex explicitly read one Core skill (`handoff-authoring`) and one Audio skill (`audio-verification`); that does not show every Core or Audio skill was exercised. The earlier probe had no Registry tool, so it does not establish Registry access. A later isolated Codex candidate with a portable `mcp.json` called the live Registry successfully, and Claude called it via its existing manifest. ChatGPT Work Registry integration remains untested. A later isolated Codex installation fetched published Core v0.2.6 from GitHub using the updated marketplace entry and successfully queried the live Registry. A user's own environment may have a separately configured Registry; that is local state, not established by these docs. Of the local plugins, the last four were discovered and installed in an isolated Codex configuration (see the verification notes below), but their live MCP connections and cross-runtime skill behaviour require separate verification. Of these, `property` currently has a Claude manifest rather than a Codex overlay (`foundations` and `legal-os` have Codex overlays; `bouch-game-assets` has a root `plugin.json` and a Claude manifest, but no Codex overlay).

## Install and validate

For Codex, add this repository as a marketplace if necessary with `codex plugin marketplace add paulieb89/bouch-plugins` (add `--ref <branch-or-tag>` to test an unmerged branch or a specific release), then install `bouch-supervision@bouch-plugins` or `bouch-engineering@bouch-plugins` with `codex plugin add`. Use the intended published ref for the version you want. An existing `bouch-plugins` source may already be configured; inspect it before adding or switching sources. Both catalogues in this repository are named `bouch-plugins`, but existing installations can still use the distinct `bouch-local` identity from earlier testing; they retain it until explicitly migrated. Restart or start a fresh session to pick up installed skills. For Claude Code, register this repository as a marketplace and install `bouch-engineering@bouch-plugins`, or test directly with `claude --plugin-dir <repository>/plugins/bouch-engineering`. `claude plugin validate <plugin-directory>` validates each Claude manifest and skill; validate the repository root separately for the Claude marketplace.

ChatGPT Work workspace import is a separate distribution step: its GitHub import must be given a repository/ref containing the committed marketplace and plugin files, with access to that repository. A successful local Codex install does not establish workspace import, GitHub sync or skill activation. See [workspace import documentation](https://learn.chatgpt.com/docs/enterprise/plugin-management) and [portable plugin packaging](https://developers.openai.com/plugins/build/plugins). No publishing or workspace import is implied by these instructions.

## Existing capability audit

The audit was made against a `bouch-agent-core` checkout newer than the earlier `v0.2.4` pin; the catalogue now pins the published `v0.2.6` (commit `df1d28e27c4d466558c9c46b40b5d2ca168c96d2`). Core remains independently usable and is not modified or copied here:

| Core skill | Assessment |
| --- | --- |
| `handoff-authoring` | Reusable for substantial handoffs; the supervisor includes only the minimal continuity it needs. Keep the detailed template canonical in Core. |
| `evidence-freeze` | Specialized preservation of verified baselines. Keep in Core; the Engineering skill addresses evaluating and attributing evidence before drawing conclusions, without requiring a freeze. |
| `environment-recon` | Useful when a capability surface has genuinely drifted; native discovery and a bounded check suffice for ordinary work. |
| `harness-extension` | Specialized when a real capability gap needs an extension; keep optional in Core. |
| `prime-authoring` | Useful when authoring an established project-specific prime; not needed for ordinary recovery. |
| `bouch-project-routing` | Historical assessment, made against the earlier Core: BOUCH orientation with stronger Core/registry framing; do not impose it on these plugins. Core `v0.2.6` is now published and pinned by the catalogue, but this assessment has not been re-made against it. Revisit separately if its own users need current architectural language. |

The previous supervision skill's Runner and Notion directions are superseded by the current architecture. Generic implementation, review, testing and agent dispatch skills were not recreated. The evidence-assessment skill is a first experiment, not a claim that its additional value over both native agents has been proven; evaluate it against real cases before expanding the package.

## Initial verification — 2026-11-07

- Claude Code 2.1.319 validated each plugin and the Claude marketplace. Its public-directory checks additionally reported missing license and icon metadata; those are listing checks, not failures of local plugin validation. Public submission has not been attempted.
- Both plugins installed from the earlier source checkout (a separate checkout, not this reconciled one) into an isolated Claude configuration; `claude plugin details` listed their respective skills. A separate direct `--plugin-dir` Claude session invoked `bouch-engineering:engineering-evidence`; its native session recorded the expanded skill and response.
- Codex installed both plugins from the earlier `bouch-local` test catalogue. A fresh Codex CLI session loaded the installed `engineering-evidence` skill and answered a missing-test-output scenario. This demonstrates loading and a narrow invocation, not comparative effectiveness.
- A fresh read-only Codex session used the installed supervision skill to recover this repository's dirty state and inspect the Claude session. It identified the outdated supervision Codex-overlay version; that mismatch was corrected after its observation. The Claude session was a skill invocation, not an implementation task, so this is not an end-to-end delegated implementation and review test.
- A new isolated Codex environment registered the GitHub test branch `test/bouch-supervision-engineering` and installed both plugins as `bouch-plugins`. This was a CLI test; it was not the desktop marketplace and not GitHub-synced Work.
- The published `test/bouch-marketplace-reconcile` branch was registered in a fresh isolated Codex CLI environment, and all three plugins were discovered and installed. This does not test the desktop marketplace UI or Work GitHub sync.
- `foundations`, `property`, `legal-os` and `bouch-game-assets` were all discovered and installed in an isolated Codex configuration. The first isolated run could not complete a model session because that configuration was unauthorized (not signed in, HTTP 401), so it verified nothing about skill activation or MCP behaviour. In a later Codex run with Foundations and Legal OS both enabled, Codex logged a duplicate `ledgerhall` server name and selected the Foundations declaration. Both configurations use the same endpoint. Codex exposed 76 direct `ledgerhall` tools and successfully executed one read-only `gov_govuk_search` for bank holidays. A second isolated Codex session with only Legal OS enabled also successfully called `ledgerhall` `gov_govuk_search` for bank holidays (count 1), with no duplicate-name warning. The both-enabled test therefore still emits the duplicate warning, but its chosen shared connection works for the single tested operation. Neither test demonstrates every skill or scenario, and the identical declarations are not automatically deduplicated without a warning.
- A cloud v0.1.1 of the supervision plugin was observed in ChatGPT Work. Separately, the user reported using the supervision plugin in Work to recover a project. That is a user report of use; it has not been independently verified here, and no transcript or activation evidence was inspected. Verified cloud sync status is a different matter: GitHub sync between this repository/ref and the Work copy is not established. The GitHub importer needs an accessible repository/ref containing these files and a workspace import. Do not infer sync or a successful import from local Codex tests, the observed cloud version or the user's report of use.
